### 2. Cache-Control on authenticated responses

**Verdict: confirmed missing.** The only `Cache-Control` set anywhere is on
the event stream (`server.ts:1183`, `no-cache, no-transform`). A live
authenticated response (`GET /api/attendance/:studentId`) came back with no
`Cache-Control` header and a weak `ETag`. Phase 1 item 5 applies.

### 3. Upload file checks

**Verdict: confirmed, type is trusted from the client.** Both multer
instances compare the file extension with the client-supplied MIME type
(`server.ts:1333-1346`, `server.ts:1363-1372`); the photo routes then check
`req.file.mimetype` again. Nothing reads the file's first bytes. Upload
routes: `POST /api/attendance`, `/api/attendance/:id/resubmit`,
`/api/supervisor/attendance/record`, `/api/complaints`,
`/api/complaints/supervisor`, `/api/tasks`, `PUT /api/tasks/:id`,
`/api/tasks/:id/submit`, `/api/documents`. Files are held in memory, so
there is no temp file to remove.

### 4. Push payloads and notification creation

**Verdict: confirmed, payloads include a `url`.** `sendWebPush`
(`server.ts:198-243`) sends `title`, `body`, `notificationId` and `url`.
The `url` comes from `pushTargets` (`server.ts:166-196`): one page per
notification `type` per role, with a per-role fallback. It is a page, not
the specific record. Phase 2 item 12 is therefore already satisfied; Phase

### 5. Attendance times

**Verdict: confirmed, server time throughout.** Time-in inserts `NOW()`
(`server.ts:2193`); break, break-end and time-out set `NOW()`
(`server.ts:2306`, `2384`, `2473`). The connection's time zone is
Asia/Manila. The client sends no timestamps for these.

`PUT /api/attendance/:id/late-time-out` (`server.ts:2697` onward) is the
one route that accepts a client time. It checks that: `time_out` parses as
a date; the reason has at least 5 characters; the log is the student's own
and has no time-out yet; the log is from an earlier day; the time is after
the last recorded time (break end, break start, or time-in); it is not in
the future; and it is within 16 hours of time-in (`MAX_SHIFT_HOURS`,
`server.ts:2695`, `2760`). The log returns to Pending for the supervisor.

### 6. Liveness ticket

**Verdict: confirmed.**
- Issued by `POST /api/attendance/liveness-challenge` (`server.ts:1994`).
- Format: a JWT from `jsonwebtoken` 9.0.3 `jwt.sign` with no `algorithm`
  option, so HS256, signed with `JWT_SECRET` (`server.ts:2002`).
- Claims: `purpose: "liveness"`, `prompts` (two of blink, smile, turn-left,
  turn-right), `spare` (a third), `sub` (the student id), `exp` 10 minutes
  after issue (`LIVENESS_TICKET_MINUTES`, `server.ts:1905`).
- Validated in `readLivenessReport` (`server.ts:1935-1990`): signature and
  expiry via `jwt.verify`; `purpose` must be `liveness`; `sub` must equal
  the student timing in; the report must list every prompt on the ticket,
  plus the spare when the light check was not `passed`.
- Not single-use: the same ticket could be presented twice inside its 10
  minutes. The unique index on `(student_id, date)` means only one time-in
  per day can result. A sign-in token is rejected as a ticket (no
  `purpose`), and a ticket is rejected as a sign-in token (no `role`).

### 7. Account wipe

**Verdict: confirmed.** `POST /api/coordinator/accounts/wipe`
